# Почему конфиг перестал работать после переноса сервера

## Контекст переноса

В коде явно зафиксирован переход с одного сервера на другой:

- **Старый сервер (OLD_IP):** `89.40.233.3`
- **Новый сервер (NEW_IP):** `194.48.142.252`

Логика «миграции» в коде: при выдаче ссылки пользователю подменяется IP в VLESS URL со старого на новый.

---

## Как устроена выдача конфига

### Сценарий 1: У пользователя уже есть ссылка в БД

1. Пользователь нажимает «Подключиться».
2. `cook_user_xray_link(..., force_rotate=False)` вызывает `get_urls_from_db()`.
3. Из БД приходит **старая** ссылка, сохранённая ещё для `89.40.233.3`, например:
   `vless://uuid@89.40.233.3:443?type=tcp&security=tls&sni=...#
4. Дальше для каждой ссылки вызывается `update_vless_url_ip(url, new_ip="194.48.142.252")` — подмена IP на новый.
5. Если подмена изменила URL — новый URL сохраняется в БД и отдаётся пользователю.

Итог: при каждом запросе ссылки из бота пользователь должен получать уже ссылку с **новым** IP, если парсинг URL сработал и замена применилась.

### Сценарий 2: Пользователь не запрашивал ссылку заново

- В приложении (v2rayN, Shadowrocket и т.п.) остаётся **старая** ссылка с `89.40.233.3`.
- Бот и БД тут ни при чём — клиент продолжает стучаться на старый IP.
- Старый сервер выключен/перенастроен → конфиг «перестал работать».

**Вывод:** после переноса пользователю нужно заново получить ссылку в боте и подставить её в клиент (или импортировать заново).

---

## Причины, по которым конфиг может не работать даже с новой ссылкой

### 1. Парсинг URL не сработал — в ссылке остался старый IP

В `update_vless_url_ip()` используется `get_vless_info(vless_url)`. Если он возвращает `None`:

- в коде делается `return vless_url` — **ссылка возвращается без изменений**;
- пользователь продолжает получать ссылку с `89.40.233.3`;
- в БД тоже не сохраняется обновлённая ссылка (мы сохраняем только когда `updated_urls != urls`).

Когда `get_vless_info` может вернуть `None`:

- нестандартный формат (пробелы, переносы, лишние символы в `vpn_url` в БД);
- URL обрезан или повреждён;
- нестандартное кодирование (например, fragment с `#` в другом виде).

Итог: один тихий сбой парсинга — и все старые ссылки продолжают уходить с старым IP.

### 2. На новом сервере нет этого пользователя (UUID)

- Раньше пользователь был создан на старом XRay (`ex.sh add`, конфиги в `/root/easy-xray`).
- После переноса возможны два варианта:
  - **Вариант A:** на новый сервер перенесли данные easy-xray (те же конфиги, те же UUID). Тогда достаточно заменить в ссылке IP на новый — конфиг должен работать.
  - **Вариант B:** новый сервер поднят «с нуля», старые конфиги не переносились. Тогда на новом сервере **нет** этого UUID. Бот по-прежнему отдаёт ссылку с новым IP, но тем же UUID. XRay на новом сервере такого пользователя не знает → соединение не устанавливается.

В случае B пользователю нужно заново получить конфиг: на новом сервере должен выполниться `ex.sh add user_id`, тогда появится новый (или тот же) UUID и рабочий конфиг. Сейчас это происходит только при `force_rotate=True` или когда в БД у пользователя ещё нет `vpn_url`.

### 3. Разный порт / TLS (SNI) на новом сервере

В коде меняется **только** хост в `uuid@host:port`; query (в т.ч. `sni=`) и fragment не трогаются. В большинстве случаев этого достаточно. Но если на новом сервере:

- другой порт для VLESS;
- другой домен/сертификат для TLS,

то старая ссылка с новым IP может быть некорректной (порт или SNI не совпадают с конфигом XRay). Тогда соединение тоже может не подниматься.

### 4. Enforcer приостановил пользователя (suspend)

Enforcer раз в N минут делает на XRay `ex.sh suspend` для пользователей с истёкшей подпиской. После suspend трафик по этому UUID не идёт. Если подписка не продлена, конфиг «не работает» независимо от переноса. Это не баг миграции, а бизнес-логика.

---

## Что сделано в коде для исправления

1. **Надёжная замена IP при любом формате ссылки**
   - Используются константы `OLD_IP` и `NEW_IP`.
   - Если `get_vless_info()` отработал — подмена по разобранным полям (как раньше).
   - Если `get_vless_info()` вернул `None` — выполняется **fallback**: простая замена подстроки `OLD_IP` на `NEW_IP` в URL. Так даже при сломанном парсинге старый IP не уйдёт в ответ и в БД.

2. **Явный список старых IP**
   - В коде задаётся список старых адресов (сейчас `[OLD_IP]`). При необходимости можно добавить несколько старых хостов (если миграций было несколько).

3. **Рекомендация после переноса**
   - Пользователям: один раз нажать «Подключиться» в боте и заново вставить полученную ссылку в клиент.
   - Если на новом сервере не переносили easy-xray, а ставили с нуля — нужна повторная выдача конфига (например, кнопка «Обновить ключ» с `force_rotate=True` или массовая перевыдача по скрипту с вызовом `cook_user_xray_link(..., force_rotate=True)`).

## Краткий чеклист после переноса

| Проверка | Действие |
|----------|----------|
| В БД в `vpn_users.vpn_url` остался старый IP? | После правок код при следующем «Подключиться» заменит IP и обновит запись. |
| Пользователь не обновлял ссылку в клиенте? | Нужно заново получить ссылку в боте и подставить в приложение. |
| Новый сервер без переноса конфигов XRay? | Нужна перевыдача конфигов с `force_rotate=True` (новый add на новом сервере). |
| Подписка истекла? | Продлить подписку; после оплаты бот сделает resume на XRay. |
| Другой порт/SNI на новом сервере? | Привести конфиг XRay к тем же порту/SNI или доработать код под новые параметры. |
